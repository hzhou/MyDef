1 Introduction

1.1 Introduction to MyDef

MyDef is a general-purpose preprocessor, in the sense that it processes input and generates output, rearranging blocks of text based on a small but powerful set of preprocessing directives as well as expanding macros that are marked with special syntax. MyDef adds a meta-layer on top of any programming language, which allows factoring code and customizing syntax at a higher level of abstraction.

A typical programming language consists of a semantics layer and a syntax layer. The former defines entities such as data types, variables, and functions and their mechanisms; the latter defines the textual form that describes these entities. MyDef works purely on the syntax layer and provides extra control over how code can be written and read.

At its base level, MyDef is used for code factoring and code rearrangement. The former covers cases such as boilerplate code and repetitive code. The latter covers cases such as organizing code in a top-down form or grouping semantically related definitions, types, variables, and code together. With MyDef, it is possible to put all feature-related code in a single file, e.g. feature_A.def, and selectively including or excluding features becomes a matter of including or commenting out the inclusion of feature_A.def in the main file. This is in contrast to the common practice of scattering feature-related code across source files with #ifdef.

1.2 Problems and Bugs

If you encounter problems with MyDef, please feel encouraged to raise an issue at https://github.com/hzhou/MyDef/issues. You are also welcome to send email to mydef at hzsolutions.net. However, there is no guarantee that your issues or questions will be addressed in any particular time frame.

Because MyDef works only on the syntax layer, almost all of its errors will result in syntax errors, and typical language compilers are very good at catching and reporting syntax errors. Syntax errors are generally easy to fix. The base features of MyDef are fairly robust. However, the development of MyDef is constantly adding and experimenting with new features. In addition, due to the flexibility of MyDef, users can develop custom plugins that introduce features that are fragile in nature. If you encounter errors from using certain features, in addition to learning more about the feature, there is always the option of bypassing the feature altogether. MyDef's syntax is designed to be distinct from most language syntax. You can always write your code in vanilla form and MyDef will pass it to the output directly.

1.3 Using this manual

This manual contains a number of examples of MyDef input and output, and a simple notation is used to distinguish input, output, and error messages from MyDef. Examples are set off from the normal text and shown in a fixed-width font, like this 


page: test
    module: perl
    $print Hello World!

To illustrate command-line examples, a shell prompt '$ ' will be shown along with the command-line input, while the program output will be shown without the prompt, like this: 


$ mydef_run test.def
PAGE: t
    --> [./t.pl]
perl ./t.pl
Hello World!

2 Installations

MyDef repositories are separated into a base repository and individual output-module repositories. Output modules depend on the MyDef base code and implement language- or application-specific features. The base repository implements features that are common to all output modules.

2.1 install base MyDef

Check that your system has perl, make, and git installed. To install MyDef for the first time, use the bootstrap script as follows: 


$ git clone https://github.com/hzhou/MyDef.git
$ cd MyDef
$ sh bootstrap.sh

By default, bootstrap.sh installs into $HOME/bin, $HOME/lib/perl5, and $HOME/lib/MyDef. In order to make MyDef work, you also need to set the following environment variables, preferably inside your ~/.bashrc: 


export PATH=$HOME/bin:[rest of your path]
export PERL5LIB=$HOME/lib/perl5
export MYDEFLIB=$HOME/lib/MyDef
If these environment variables are set first, bootstrap.sh will install into the specified destination instead.

It is also recommended to keep the MyDef repository after installation. You will need the base repository to install additional output modules. For that matter, you will also need to set the environment variable MYDEFSRC: 


export MYDEFSRC=[path to your MyDef repository]

The MyDef repository can be updated by running git pull. During the bootstrap process, a Makefile is created, so upon updates or files being locally edited, you may simply run make to install the updates: 


$ make
$ make install
You may need to run mydef_make to update the Makefile when new files have been added or removed from the repository.

2.2 What is installed

The following are installed in $HOME/bin (they are all perl scripts):

  • mydef_page: compiles from .def to output(s).
  • mydef_make: checks .def files in the current folder and config file if exist, output Makefile.
  • mydef_run: convenient script to compile and run a single program.
  • mydef_install: installs files into $MYDEFLIB, $PERL5LIB, or the first location of $PATH.

The following are installed in $PERL5LIB:

  • mydef.pm: defines global variables, loads output_modules, etc.
  • MyDef/parseutil.pm: defines routines for loading .def files.
  • MyDef/compileutil.pm: defines routines for translating into output, defines macros and preprocessing functions.
  • MyDef/dumpout.pm: defines routines for final output.
  • MyDef/utils.pm: defines some helper routines.
  • MyDef/output_general.pm: the default output module.
  • MyDef/output_perl.pm: output module for perl code.

The following are installed in $MYDEFLIB:

  • std_general.def: macros automatically loaded by output_general.pm; by default it is empty.
  • std_perl.def: macros automatically loaded by output_perl.pm

These are the essential files that are needed for basic MyDef functions. There may be additional files being installed, which may add debugging functions or extra def libraries.

2.3 Install additional output_modules

The base MyDef installs output_general.pm, which is used by default when no module option is given -- in the config file, the .def source, or on the command line of mydef_page or mydef_run. output_general only translates base MyDef macros and preprocessing directives, and it can be used to generate any text files, including .txt, .pl, .c, or source code for any programming language. The extension of the output files can be individually specified inside the .def source. By default, .txt is assumed.

Although the output_general module can be used for any programming language, language- or application-specific output modules can be developed to add language-specific features. For example, the output_perl and output_c modules can automatically add semicolons or curly braces as needed so the programmer can optionally omit them. output_c can also manage automatic variable and function declarations with some type inference logic. As another example, output_win32 can add features that automatically manage WNDPROC message handlers to make Win32 programming more flexible.

Other than output_general and output_perl, all output modules have their own repositories and need to be individually installed. To install these additional output modules, you need to make sure that you have the updated base MyDef repository and that the environment variable $MYDEFSRC points to its location. The installation process is very similar for all modules. For example, the output_c module can be installed like this: 


$ git clone https://github.com/hzhou/output_c.git
$ cd output_c
$ mydef_make
$ make
$ make install

It will compile and install output_c.pm into $PERL5LIB/MyDef/, std_c.def and some other standard def libraries into $MYDEFLIB.

The following output_modules are currently available from https://github.com/hzhou/:
output_c, output_python, output_java, output_www, output_win32, output_xs, output_fortran, output_pascal, output_tcl, output_go, output_rust, output_glsl
Not all modules are equally developed or tested.

3 Getting Started

This chapter walks through creating your first MyDef project step by step. By the end, you will understand the basic workflow and core concepts. We assume you have already installed MyDef following the instructions in the Installations chapter.

3.1 Hello World with output_general

Let's start with the simplest possible example. Create a file called hello.def with the following content: 


page: hello
    Hello, World!

This defines a single page named hello. The indented line beneath it is the page's content. Now compile it: 


$ mydef_page hello.def
PAGE: hello
    --> [./hello.txt]

mydef_page read the .def file, processed the page, and wrote the output to hello.txt. Since we did not specify a module, output_general was used by default, which produces .txt files. The output file contains exactly what we wrote: 


Hello, World!

That is the core of MyDef: you write .def files and compile them into output files. With output_general, the output is plain text with macros expanded and subcodes inlined. Other output modules add language-specific features on top.

3.2 Hello World with output_perl

Now let's try generating a Perl script. Create hello_perl.def: 


page: hello_perl
    module: perl
    $print Hello, World!

The module: perl attribute tells MyDef to use output_perl. The $print syntax is a convenience provided by output_perl -- it generates a print statement with automatic quoting and newline.

Instead of compiling and running separately, we can use mydef_run to do both in one step: 


$ mydef_run hello_perl.def
PAGE: hello_perl
    --> [./hello_perl.pl]
perl ./hello_perl.pl
Hello, World!

Let's look at the generated hello_perl.pl: 


#!/usr/bin/perl
use strict;

print "Hello, World!\n";

output_perl automatically added the #! shebang line, use strict;, quotation marks, \n, and the semicolon. You wrote one line; MyDef produced correct, complete Perl.

3.3 First Subcode

A subcode is a reusable block of code. It is the primary abstraction in MyDef. Here is an example: 


page: greet
    module: perl
    $call greet, Alice
    $call greet, Bob
    $call greet, Carol

subcode: greet(name)
    $print Hello, $(name)!

subcode: greet(name) defines a block with one parameter. $call greet inlines that block with $(name) replaced by Alice. Running this produces: 


$ mydef_run greet.def
PAGE: greet
    --> [./greet.pl]
perl ./greet.pl
Hello, Alice!
Hello, Bob!
Hello, Carol!

The generated Perl looks like this: 


#!/usr/bin/perl
use strict;

print "Hello, Alice!\n";
print "Hello, Bob!\n";
print "Hello, Carol!\n";

The subcode was expanded three times, each time with a different parameter value. This is pure text substitution -- there is no function call overhead at runtime.

When you need to call a subcode many times with different single parameters, $map provides a shorthand: 


$map greet, Alice, Bob, Carol

This produces the same output as the three separate $call lines above.

3.4 First Block Call

Many code patterns have an opening part and a closing part with varying content in between. MyDef handles this with &call (block call) and the BLOCK keyword. Here is an example: 


page: wrap
    module: perl
    &call open_w, output.txt
        $(set:print_to=Out)
        $print Line 1
        $print Line 2

open_w is a subcode from MyDef's standard library. It opens a file for writing. The indented block beneath &call replaces the BLOCK keyword inside the subcode definition.

To understand the mechanism, here is a simplified version of what open_w looks like: 


subcode: open_w(file)
    open Out, ">$(file)" or die "Can't open $(file)\n"
    BLOCK
    close Out

When you write &call open_w, MyDef expands it as: 


open Out, ">output.txt" or die "Can't open output.txt\n";
print Out "Line 1\n";
print Out "Line 2\n";
close Out;

The key difference between $call and &call:

  • $call -- inline expansion. No indented block follows.
  • &call -- block expansion. An indented block follows and replaces BLOCK inside the subcode.

3.5 First Macro

Macros are compile-time text substitutions. They are defined in a macros: block and referenced with $(name) syntax: 


macros:
    greeting: Hello
    audience: World

page: macro_demo
    module: perl
    $print $(greeting), $(audience)!

This generates: 


print "Hello, World!\n";

Macros are expanded before any language processing. They work the same regardless of the output module.

For macros that are only needed locally, use $(set:...) instead of a macros: block: 


subcode: matrix_multiply
    $(set:N=4)
    $(set:m=mat[$1][$2])
    $for i=0:$(N)
        $for j=0:$(N)
            $(m:C,i) += $(m:A,i) * $(m:B,j)

$(set:...) macros expire at the end of their enclosing scope, keeping the namespace clean.

3.6 Project Workflow

For a single-file program, mydef_run is all you need. For larger projects with multiple output files, the typical workflow uses mydef_make to generate a Makefile.

Start by creating a project directory with a config file: 


$ mkdir myproject
$ cd myproject

Create a config file specifying where output goes and which module to use: 


module: perl

Create your .def source files, then run mydef_make: 


$ mydef_make
Create output folder out ...

This scans all .def files in the directory, determines their dependencies, and generates a Makefile. Now you can use the standard make workflow: 


$ make

After editing .def files, simply run make again -- it will only recompile files whose dependencies have changed.

The typical development cycle is:

  • For quick experiments: edit .def, run mydef_run file.def
  • For projects: edit .def, run make (after initial mydef_make)
  • To install: run make install (if an install_def.sh is set up)

4 Basic MyDef syntax

Before diving into details, here is a quick reference of the core concepts in MyDef:

Concept Definition Usage Scope
Page page: name compiled automatically into an output file file
Subcode subcode: name(params) $call name global or page
Block call subcode with BLOCK keyword &call name + indented block nested
Macro macros: block $(name) global or page
Dynamic macro $(set:name=value) $(name) current scope
fncode fncode: name(params) target language function call global

4.1 Basic structure of .def file

The basic structure of .def file is indentation based. An example .def file may look like this: 


include: common.def
include: macros/utils.def

# This is a comment
page: test
    Line 1
    Line 2
    $call A
    lines after

subcode: A
    line a - $(msg_a)
    line b - $(msg_b)

macros:
    msg_a: this is message a
    msg_b: this is message b

Compiling this with mydef_page produces a file test.txt containing: 


Line 1
Line 2
line a - this is message a
line b - this is message b
lines after

The $call A was replaced by the body of subcode: A, and the macros $(msg_a) and $(msg_b) were expanded to their values. This is the essence of MyDef: subcodes are inlined and macros are expanded, producing the final output.

At the top indentation level, only headings include:, page:, subcode:, and macros: are recognized by parseutil.pm. However, any additional lines not under these headings do not cause MyDef errors. They will be silently ignored. So a Knuth-style literate programming can be achieved with MyDef by freely mixing documentation (at the top indentation level or under any unrecognized headings) and code (under these recognized headings).

Explicit comments can be introduced with # at any indentation level or between code or at the end of any lines.

include: adds additional files to a list and they will be loaded in the order of addition. Note that this is different from the C preprocessor. A file can be included multiple times but will only be loaded once. The included file will be searched for in the current working directory, include_path settings in the config file, and the environment variable $MYDEFLIB.

page: defines the output file name and its main code. Each line in the main code will be copied, macro-expanded, or translated, and finally dumped to the output file. For output modules other than output_general, there may be additional lines inserted or appended to the main code. For example, output_perl will automatically insert #! lines and use strict; for Perl scripts.

subcode: defines blocks of code that can be inserted into main code or another subcode by syntax like $call codename. The syntax resembles function definitions and function calls in a programming language. However, it is more appropriate to think of subcodes as merely multi-line macros that are expanded at the block or line level. Their usage is very similar to inline macros and they will be expanded regardless of the underlying language syntax. subcodes allow reorganization of code according to higher logic than the semantics of a programming language.

macros: defines a set of name-value definitions. They are used as inline macros. To use these macros and have them expanded in the output, one can use syntax like $(msg_a). This syntax was chosen to avoid collision with common language syntax. Having macros stand out makes the subtle differences between macros and certain programming language entities such as variables and functions explicit. This is in fact helpful for both writing and reading programs.

The code block under page: is actually a subcode with name main. In fact, it is the same to declare main code like this: 


page: test
    subcode: main
        line 1
        line 2
        ...

Upon compilation, each page output looks for a main subcode. If not found, the output will be blank regardless of how many subcodes or macros are defined in the def files.

Not all def files need to contain page: directives. In practice, most def files contain only macro and subcode definitions and are included via include: into the main def file.

The overall structure of def files is declarative. The order of include:, page:, subcode:, and macros: does not matter -- in most cases. The few cases where order does matter will be discussed in the following chapters.

Indentation needs to be strictly observed directly under page:, subcode:, and macros:. More specifically, all lines that are supposed to be under the directive need to have indentation at or deeper than the first line's indentation. Otherwise, part of the code block or definitions may be ignored during parsing. The code under subcode, which includes the main code under page, may contain additional indentation within. All this internal indentation will be preserved and passed to output. However, during parsing, the leading spaces of a line are stripped and encoded as just the indentation level. Upon output, the indentation is added back by inserting 4 spaces for each indentation level. So the output code may look slightly different from what is defined in subcode. For most languages, leading spaces are insignificant and only the indentation level matters, so MyDef's indentation treatment should not pose any problem. In fact, it helps make the output code more readable.

4.2 Scope

Both subcode and macros can be nested and they follow the visibility of the scope. It is possible to structure code like this: 


macros:
    A: global macro

subcode: A
    global subcode.
    Inline macros and subcodes have different namespace.

page: test
    m: page-level macros can be directly defined here, but only directly under page: directive
    # page defines a page scope

    macros:
        p: this is also a page scope macros

    subcode: main
        These subcodes (include main) are defined at the page scope
        $call A # works, global scope is visible
        $call a # works, page scope is visible
        $call c # won't work, issues error message

    subcode: a
        This is at page scope

        subcode: c
            nested subcode

        macros:
            q: only visible inside subcode: a

Scopes are observed during expansion time. In the above example, normally subcode: a inside page is not visible to subcode:A. However, when A is called inside the page, the scope of subcode:A becomes nested under the page scope, and subcode: a becomes accessible. While this expansion-time scoping rule is flexible and can be used to enhance code readability in certain scenarios, it is also very easy to abuse and create spaghetti code. Apply common sense.

4.3 Dynamic inline macros

Using the macros: directive is not the only way to define inline macros. Because the macros: directive has to be used away from where the macros are being used, it is only useful for macros that need to be visible across larger scopes. For local macro usage, there is another syntax to define them: 


subcode: A
    $(set:a=A_very_long_array_variable[i])
    $(a) = $(a) * $(a)

At global context, long and descriptive names are desirable; but at small local context, short names are desirable. Macros provide simple and straight solutions. It is nice to be able to define it right where it is being used so programmers don't have to scroll far to infer the meaning. The local macro automatically expires at the end of block context, which saves the worry of name pollution.

4.4 Subcode with parameters

There are two ways to pass parameters into a subcode. We can always set macros right before we $call the subcode as mentioned in the previous section. The drawback of this method is that the parameter signature is not defined where the subcode is defined. This can be remedied by adding comments, but is nevertheless less than ideal. Also, the calling interface is somewhat clumsy.

We can directly define subcode with following syntax: 


subcode: A(greet, name)
    printf("$(greet), $(name)!\n");

page: t
    $call A, Hello, World
    $call A, Howdy, Guest

Multiple parameter names can be defined in the subcode: line inside parentheses, separated by commas. Correspondingly, $call needs to append actual values for the parameters after the subcode name, separated by commas. In implementation, parameters are essentially the same as inline macros and are used equivalently.

The number of values passed in at $call time must match the number of parameters defined in the subcode. A mismatch will raise errors. The values at $call are split simply by comma (and any spaces that follow). This can pose a problem when the value itself contains a comma. In practice, there are a few heuristic implementation rules that make these situations tolerable. For one, if the comma is enclosed in parentheses or quotation marks, it will not be treated as a separator: 


subcode: A(greeting)
    printf($(greeting));

page: t
    $call A, "Hello, World!\n"

Of course this will not automatically solve all use cases. In fact, in some cases you may want the comma to act as a separator despite quotation marks or parentheses around it. For tricky situations, MyDef may choose simply not to provide support. Supporting tricky situations often complicates both code and usage, and sometimes explicitly not supporting them may be the better option. You can always avoid tricky feature usage by not using the feature at all and writing your code directly, letting MyDef pass it through to output.

That said, in the case that you want the usage to absorb all remaining text as a single parameter, there is a syntax for that: 


subcode: A(greet, @names)
    $print $(greet), $(names)!

page: t
    $call A, Hello, Alice, Bob, and Carol

Prepending @ to the last parameter name in the subcode: definition signals the MyDef compiler to absorb all remaining text at $call time. Obviously, @param will only work for the last (or only) parameter. In addition, @param also signals the MyDef compiler that it is OK to have empty values for that parameter, so MyDef will not raise an error even when the value is missing at $call time. Use it with caution.

4.5 Block call

One of the main purposes of subcode is to capture text patterns. A common pattern may consist of an opening part and a closing part. In many languages and other implementations, this kind of pattern requires two or more separate subcode definitions, called separately as well. It is ugly. For this type of pattern, MyDef supports the &call syntax: 


subcode: tag(name)
    <$(name)>
        BLOCK
    </$(name)>

page: t
    &call tag, html
        &call tag, body
            &call tag, h1
                Hello, World!

Note that BLOCK is indented one level inside the opening and closing tags. This indentation is preserved in the output, so nested block calls produce properly indented results: 


<html>
    <body>
        <h1>
            Hello, World!
        </h1>
    </body>
</html>

If BLOCK were at the same indentation level as the tags, the output would be flat with no nesting indentation.

&call requires an indented block following the call, where code is expected to be inserted inside the subcode expansion, replacing the keyword BLOCK. BLOCK is one of a few special MyDef keywords in addition to the $(macro...) syntax.

The code that replaces BLOCK will have its own scope and is nested inside the subcode being called, and therefore can access all macros and subcodes that are defined within. For example, you may use block call purely for context: 


subcode: Parsing(line)
    BLOCK

    subcode: parse_string
        $if $(line)=~/"([^"]*)"/
            BLOCK
    subcode: parse_number
        ...

page: t
    &call Parsing, text
        &call parse_string
            $print got string $1

4.6 $call vs &call

To summarize the difference between the two calling conventions:

  • $call name -- inline expansion. The subcode body is inserted directly. No indented block follows.
  • &call name -- block expansion. An indented block must follow. That block replaces the BLOCK keyword inside the subcode body.

Both use the same subcode definition. A subcode with BLOCK can be invoked either way: $call skips the BLOCK placeholder, while &call fills it. Note that using $call on a subcode containing BLOCK will produce a warning: BLOCK called out of context!. The warning is harmless -- the BLOCK line is simply omitted from the output. Consider: 


subcode: section(title)
    --- $(title) ---
    BLOCK
    --- end $(title) ---

page: t
    # inline call -- BLOCK is skipped:
    $call section, Empty

    # block call -- BLOCK is filled:
    &call section, Content
        Line 1
        Line 2

The output would be: 


--- Empty ---
--- end Empty ---
--- Content ---
Line 1
Line 2
--- end Content ---

4.7 Map call

For subcodes with a single parameter, sometimes it is desirable to call them multiple times with various parameters concisely. For this, we can use the $map call: 


subcode: greet(name)
    push @guests, "$(name)"
    $print Hello $(name)!

page: t
    module: perl
    $map greet, Alice, Bob, Carol

The subcode is called once for each parameter. The output t.pl would be: 


#!/usr/bin/perl
use strict;

push @guests, "Alice";
print "Hello Alice!\n";
push @guests, "Bob";
print "Hello Bob!\n";
push @guests, "Carol";
print "Hello Carol!\n";

Less often used, the $map syntax can also be used with subcodes that need multiple parameters by sharing common parameters: 


subcode: A(greet, name)
    $print $(greet), $(name)!

page: t
    module: perl
    $map A(Hello), Alice, Bob, Carol

Here Hello is passed as the first parameter to every call, and the remaining parameters are mapped over one at a time.

One of the benefits of $map call is to allow certain use of macros: 


macros:
    Guests: Alice, Bob, Carol

subcode: A(greet, name)
    $print $(greet), $(name)!

page: t
    module: perl
    $map A(Hello), $(Guests)

The macro is expanded before mapping, so both of the last two examples produce the same statements: 


print "Hello, Alice!\n";
print "Hello, Bob!\n";
print "Hello, Carol!\n";

It should be noted that there are preprocessing directives that will be introduced in a later chapter to achieve a similar result.

4.8 Nest call

A similar but even more exotic syntax is the $nest call. It works with a block subcode and nests the block calls, one level per parameter: 


subcode: each(x)
    $foreach $$(x) in @$(x)s
        BLOCK

page: t
    module: perl
    my @sizes = ("small", "large")
    my @colors = ("red", "blue")
    $nest each, size, color
        $print $size $color

$nest is the syntax sugar for: 


&call each, size
    &call each, color
        $print $size $color

The output t.pl would be: 


#!/usr/bin/perl
use strict;

my @sizes = ("small", "large");
my @colors = ("red", "blue");
foreach my $size (@sizes) {
    foreach my $color (@colors) {
        print "$size $color\n";
    }
}

Running it prints every combination: 


small red
small blue
large red
large blue

$nest is most useful when the nesting is deep, or when the list of levels comes from a macro: if a macro dims holds the list of levels, $nest each can simply take $(dims) as its parameters.

4.9 Multiply defined subcode

A common usage pattern is to use subcode as place holders, for example 


page: t
    $call @main_init
    $call main_loop
    $call finish

main_init is a placeholder that will have initialization code related to many different features. The @ prepended to the name suppresses warnings even when the subcode is not defined, perfect for placeholders.

Now it is not desirable to mix code related to different semantic groups together even though they all need to happen at the same runtime context. For that, MyDef allows a subcode to be multiply defined. 


# ---- feature_A.def ----

subcode:: main_init
    feature A related initialization

subcode: other_subcode_related_to_feature_A
    ...
            

# ---- feature_B.def ----

subcode:: main_init
    feature B related initialization

subcode: other_subcode_related_to_feature_B
    ...

Pay attention to the double colons after subcode. If double colons are omitted, only the first subcode: definition will get loaded. This is where include files loading order matters. Unintentional subcode name collision should be avoided.

Finally in the main .def file, we can simply include the files: 


include: feature_A.def
# include: feature_B.def  # selectively disable feature B

page: t
    $call @main_init
    ...

To see the effect, here is the same pattern in a single file: 


subcode:: main_init
    feature A initialization

subcode:: main_init
    feature B initialization

page: t
    module: general
    $call @main_init
    main loop

Both definitions are concatenated, so the output t.txt is: 


feature A initialization
feature B initialization
main loop

If the double colons are replaced with single colons, only the first definition is kept and mydef_page warns about the second one: 


Not overwriting subcode main_init: [t.def - 1] -> [t.def - 4]

and the output becomes: 


feature A initialization
main loop

It should be mentioned that in addition to subcode::, signifying concatenation, there are also subcode:@ and subcode:-. Both advise MyDef on what to do when subcode names collide. subcode:@ signifies lower priority. This is used to supply a default subcode definition in a library, and any colliding subcode definition will overwrite it. subcode:- is similar to subcode:: and signals that the code should be concatenated. Unlike the double colon, subcode:- always prepends the code to whichever definition was loaded earlier. It goes without saying that the effect of these special syntaxes depends on the loading order of the MyDef parser and can be difficult to follow. In general, their use should be discouraged.

4.10 subcode: _autoload

There is a special subcode called _autoload. If defined, it will be automatically called before loading the page's main code.

The function of _autoload is similar to the multiply defined subcode above except that it is called automatically. For its role, subcode: _autoload can be defined in multiple places and the code will be concatenated together even when the subcode: line does not use double colons.

4.11 DUMP_STUB

A very similar effect as multiply defined subcode is DUMP_STUB. It is used like this: 


page: t
    DUMP_STUB main_init
    $call feature_A
    $call feature_B

subcode: feature_A
    $(block:main_init)
        code initialization related to feature A
    feature A implementation

subcode: feature_B
    $(block:main_init)
        code initialization related to feature B
    feature B implementation

The output would be: 


code initialization related to feature A
code initialization related to feature B
feature A implementation
feature B implementation

DUMP_STUB is a keyword for placeholders that will be replaced at the end with a named block of code. The syntax $(block:...) places the code into that named block. The initialization code from both features was gathered into the main_init block and inserted at the DUMP_STUB position, before the feature implementations.

$(block:...) integrates with other relevant code more tightly and shares the same subcode scope. Sometimes this is more readable than the alternative of having a separate subcode.

4.12 Inline macros with parameters

It is also possible to define and use inline macros with parameters. For example: 


$(set:m=$1[$2*$(N)+$3])
$for i=0:$(N)
    $for j=0:$(N)
        $for k=0:$(N)
            $(m:C,i,j) += $(m:A,i,k)*$(m:B,k,j)

Inline macro parameters are not explicitly declared; they are simply marked by $1-9 and replaced at expansion time with a comma-separated list of values.

Only single digit following $ is significant. For example: 


macros:
    A: $11

subcode: test
    This is $(A:x) # x1

4.13 Preprocessing: $(if:...)

Basic switching logic is supported with preprocessing directives $(if:...), $(elif:...), $(else), and $(endif): 


$(if:!A)
    Code when macro A is not defined
$(elif:A=0)
    Code when A equals "0" (string comparison)
$(elif:A>10)
    Code when A is numerically > 10
$(else)
    Code for the remaining cases

Here is a reference of all supported condition forms:

Condition True when
$(if:A) macro A is defined and non-empty
$(if:!A) macro A is not defined or empty
$(if:A=val) macro A equals "val" (string comparison)
$(if:A!=val) macro A does not equal "val"
$(if:A>10) macro A is numerically greater than 10
$(if:A>=10) macro A is numerically greater than or equal to 10
$(if:A<10) macro A is numerically less than 10
$(if:A<=10) macro A is numerically less than or equal to 10
$(if:A~pat) macro A matches regex pattern (head match)
$(if:A!~pat) macro A does not match regex pattern
$(if:A or B) either A or B is true
$(if:A and B) both A and B are true
$(if:0) / $(if:1) always false / always true (for quickly disabling/enabling code)
$(if:hascode:name) subcode "name" is defined
$(if:A in x,y,z) macro A equals one of the listed values
$(if:string:A) macro A looks like a string literal
$(if:number:A) macro A looks like a number
$(if:word:A) macro A looks like a simple word

A few notes on the conditions:

  • The left side of comparison operators (=, <, >, etc.) is always treated as a macro name. The right side is a normal expression. For example, in $(if:A>$(B)), A is a macro name while $(B) is expanded.
  • or and and can combine conditions, but they are not implemented as full expressions. Nested combinations of !, or, and and may not work as expected.
  • $(if:0) and $(if:1) are special cases -- useful for quickly disabling or enabling a block of code.

For the complete up-to-date implementation, see macros_compile/preproc.def, fncode: testcondition.

4.14 Preprocessing: $(for:...)

The $for... syntax provides quick way to multiplex code: 


$(for:a in Alice, Bob, Carol)
    Hi, $(a)

$(set:namelist=Alice,Bob,Carol)
$(for:a in $(namelist))
    $(if:a=Alice)
        Hi $(a), I love you!
    $(else)
        Hi $(a)!

There is a shortcut syntax for specifying a simple range-based list: 


# reference: mydef_utils.def: fncode: get_range($a, $b)
$(for:a in 1-11) # 1,2,3,...,11
    $print $(a)

$(for:a in a-z) # a,b,c,...,z
    $print $(a)

Sometimes we may need to multiplex over multiple lists: 


$(for:a, i in x,y,z and 0,1,2)
    # x = 0, y = 1, and z = 2
    $(a) = $(i)

There is also a syntax to use &dollar(for:...) anonymously: 


$(for:Alice, Bob, Carol)
    Hi $1

$1 is used to refer to the implicit macro for each case.

Anonymous multiplexing over multiple lists also works: 


$(for:x,y,z and i,j,k)
    A_$1 = $2;

Up to nine lists are allowed, but you probably want to limit to a much smaller number.

4.15 Preprocessing: $(set:...)

We already learned that $(set:...) can be used to set local macros within the scope. What if we want to set macros to the parent scope? We can use $(set-1:...): 


$call set_macros
$print A = $(A)

subcode: set_macros
    $(set-1:A=3.14)

Direct $(set:...) won't work here as it will expire upon exit the subcode.

We also can set macros at global level using $(setmacro:...): 


subcode: section(title)
    $(setmacro:id+=1)
    Section $(id). $(title)

page: t
    $call section, Hello
    $call section, Bye

We haven't introduced the += operator yet. Intuitively, += increments the macro definition numerically.

+= works for $(set:...) and $(set-1:...) as well. However, it is difficult to track consistent macros across scopes, therefore, it makes most sense to only use these operators in $(setmacro:...).

In addition to +=, there are also -=, *=, and /=, which does their corresponding arithmetic updates. They are not as useful as += though.

There is also a string concatenation operator .=, which appends the new definition to the old one.

Very often when we need concatenate strings, we would like some separators into between the items. For that, we have another syntax: 


subcode: add_name(name)
    $(setmacro:namelist[,]=$(name))
    Hi $(name)!

page: t
    $call add_name, Alice
    $call add_name, Bob
    We have gathered: $(namelist).

Because the scoping rules, very rarely we need unset macros. When we need it, it is often only needed to shield certain macros from child scopes. For that, we have the $(unset:...). 


$(unset:A,B,C)
$call subcode_that_checks_macros

Note that $(unset:...) only unsets macros in the current scope, but will effectively shield macros defined in parent scopes. It only accepts a list of simple words.

$(set:...) sets one macro at a time, so it does not need any delimiters, and you can easily define macros with commas in them.

Sometimes it is desirable to set multiple macros in a single line. For that, we can use $(mset:...): 


$(mset:A=x,B=y,C=z)

You can only set macros in the current scope with $(mset:...), and you cannot have commas in the definitions.

4.16 Preprocessing: scope rules

Both $(for:...) and $(if:...) contains nested blocks. It should be noted that $(for:...) will create additional child scopes, but $(if:...) (and elif/else) will not.

The latter is useful as in the following case: 


subcode: greet(type, name)
    $(if:type=hot)
        $(set:greeting=It is such an honor to meet)
        $(set:ending=!!!)
    $(else)
        $(set:greeting=Hello,)
        $(set:ending=.)
    $(greeting) $(name)

4.17 Special macro syntax

MyDef implements a small set of special macro syntax for convenience: 


Type name 10 times: $(x10:NAME ) # NAME NAME ... NAME
Type name 10 times: $(x10, :NAME) # NAME, NAME,  ... NAME
List of digits: $(join:pat $1:, :1-3) # pat 1, pat 2, pat 3
Duplex list: $(join:$1_$2:, :x-z and 1-3) # x_1, y_2, z_3
Multiplex list: $(join:$1_$2:, :x-z mul 1-3) # x_1, x_2, ..., z_3

$(set:A=word)
Perl one-liners: $(eval:ucfirst("$(A)")) # Word

MyDef is written in Perl, so it is trivial to add eval and expose the entire Perl engine. There is also a similar interface for eval subcode, which essentially allows direct perl code to manipulate text transformations. However, it is necessary to understand MyDef's internal details to effectively work with the rest of MyDef processing. We'll discuss details in later chapters.

For more up-to-date details, please reference the source.

4.18 Collisions with target-language syntax

MyDef adds very little syntax of its own, but it processes the text before the target language ever sees it. A few MyDef constructs -- comments, macros, and parameter lists -- can therefore collide with ordinary text in the output language. When the output looks wrong, check the generated file and watch for warnings such as Macro ... not defined from mydef_page.

Comments: # and /*

A line starting with # is a MyDef comment and is dropped. C preprocessor lines (#include, #define, #if, #ifdef, #else, #endif, #pragma etc.) are recognized and kept. Other lines -- a shebang, or a comment in Perl, Python, or shell -- are removed.

A # with whitespace on both sides starts a trailing comment and the rest of the line is removed, even inside a string. A # that is not surrounded by whitespace is safe: 


page: t
    module: general
    x = "a # b"
    y = "a#b"

produces: 


x = "a
y = "a#b"

Similarly, a line starting with /* begins a multi-line comment that is removed through the closing */.

Workarounds:

  • Start the line with a hex escape. A leading \xNN is decoded when the output is written, so \x23!/bin/sh outputs #!/bin/sh and \x2f* ... */ outputs a C comment. Only a leading escape is decoded.
  • Define a macro for the character, e.g. H: # under macros:, and write "a $(H) b". Macros are expanded after comments are filtered.
  • Use the target language's own escape, e.g. "a \x23 b" in a Python or Perl string.

Macros: $( and $.

$( followed by a word character is a macro reference. An undefined macro expands to nothing, with a warning. This collides with shell command substitution $(date), Makefile variables $(CC), and jQuery $(document). In addition, $. is a shorthand for the macro $(this), which collides with Perl's $. and jQuery's $.ajax.

Forms that do not start with a word character are safe: $( date ), $((1+2)), $("#id"), as are ordinary variables such as $x and ${x}.

Workarounds:

  • Start the line with $: -- the rest of the line is output literally without macro expansion. (Comment filtering still applies.)
  • Define a macro for the character, e.g. D: $, and write $(D)(date).
  • Start the line with \x24, e.g. \x24(CC) -o prog. 

macros:
    D: $

page: t
    module: general
    d=$(date)            # macro "date" -- expands to nothing
    d=$(D)(date)         # d=$(date)
    $: CMD = $(CC) -c    # CMD = $(CC) -c

Commas in parameters

Parameters of $(name:...), $call, and $map are separated by commas. If a macro uses fewer parameters than given, the extra ones are silently dropped: 


macros:
    code: <code>$1</code>

page: t
    module: general
    $(code:a, b)         # <code>a</code> -- ", b" is lost
    $(code:f(a, b))      # <code>f(a, b)</code>

Commas inside parentheses, brackets, or quotes are protected, so f(a, b), [1, 2], and "1, 2" each stay a single parameter. A macro holding a comma does not help, because it is expanded before the parameters are split. Otherwise, rephrase or use an escape of the target language, such as &#44; in HTML.

Page attributes and keywords

Lines of the form word: value at the very start of a page are read as page attributes (such as module: and output_dir:) and do not appear in the output. If the output itself starts with such a line (YAML, for instance), put $: in front of it.

A few words are MyDef keywords when they appear alone on a line: BLOCK, NEWLINE, NOOP, and DUMP_STUB name. Lines starting with $call, &call, $map, and similar are always MyDef calls. Output modules add their own keywords (e.g. $if and $print).

4.19 fncode: -- function definitions

While subcode is expanded inline at compile time, many languages have their own concept of functions that are called at runtime. MyDef supports this with fncode:: 


page: t
    module: perl
    $print "3 squared is %d", square(3)

fncode: square($x)
    return $x * $x

fncode: is defined at the top indentation level, just like subcode:. The key differences are:

  • fncode: generates a function in the target language (e.g. sub in Perl, a C function in C).
  • fncode: is called using the target language's normal function call syntax, not $call.
  • Parameters are declared in the fncode: line and automatically unpacked in the generated code.

The exact behavior of fncode: depends on the output module. For example, output_perl generates sub definitions with automatic parameter unpacking from @_, and only includes functions that are actually used in .pl scripts. See the output module chapters for details.

5 Invoking MyDef

5.1 config file

The suite of MyDef tools will always check for a config file (a text file named config) in the same directory where the main .def file is located.

Strictly speaking, a config file is not always necessary. MyDef options can be set in three places: inside the .def source, on the command line, and in the config file. The config file is a convenient means to share default settings across an entire project.

When the config file is missing and we invoke mydef_make to create a Makefile, it will always create a config file, so further invocations of mydef_make will not prompt you with questions again and again.

Basic config file only contains two settings. Following is the one for the MyDef repository: 


module: perl

output_dir specifies the directory where the output files should be put. If this option is missing, the default is to put output files in the same directory of the .def sources. For big projects, some separation is desirable.

module specifies the output module to use. When this option is missing, the default is to use output_general. MyDef is written in Perl, so for its own repository the module is output_perl.

Another often used options is include_path, which is a ':' separated list of directories for searching for include: files. The option if provided gets prepended to environment variable MYDEFLIB. The current folder will always get searched first.

The output_general module does not need many options, but many language- and application-specific output modules do need additional options to control behavior. The config file can contain arbitrary options, and it is the output module's responsibility to check these options.

Internally, MyDef does not really differentiate between macros and options. Both are simply name-value pairs. Everything specified in MyDef is internally available in a global reference hash variable $MyDef::var.

5.2 mydef_page

mydef_page is the MyDef compiler. It reads in a .def (and all the included .def files included within), translates it, and writes to output files, one per page: directive. 


$ mydef_page -m[module] -o[outputdir] src.def

-m specifies output module to use. -o specifies output directory that output files will go. There should not be spaces between the option and value.

Both options can be omitted. If the module is missing, it takes from config file. If config does not exist or the module option is not set within, it will check for module option inside the source .def file. If still not found, mydef_page will complain and exit.

However, when the module option is given via command line or config file, that module will be used. And when the module option under page: directive mismatches this module, the corresponding page will be ignored. For example: 


$ mydef_page -mgeneral t.def
skipped 1 pages (due to module mismatch), use -m to override default module.

It is possible to have multiple pages defined in a single .def file. All pages that match the module option will be compiled in a single invocation. If multiple pages require different output modules, multiple invocations of mydef_page with different module options are necessary to compile every page.

-o specifies the output location. If not specified, it will search similarly in the config file. If not found, it defaults to the current working directory.

If the source .def file also specifies output_dir under the page: directive, the behavior depends on whether an absolute or relative path is given.

If an absolute path is given, it will be used as the output location.

If a relative path is given instead, it will be appended to the path given on the command line or config file, or the default . (current directory).

When everything goes well, it looks like the following: 


$ mydef_page t.def
PAGE: t
    --> [./t.pl]

If multiple pages are being compiled, each of them will be listed.

If MyDef encounters errors, there will be error messages: 


$ mydef_page t.def
PAGE: t
[t.def:4] Code A not found!
[t.def:5] Macro B not defined
--> [./t.pl]

The output file will still be produced despite the errors. It is important to pay attention to error messages.

File locations are usually reported along with errors. However, it should be noted that the current implementation of file location tracking is imprecise and can often be off by a few lines. Nevertheless, you should be able to locate the error with the information given in the error message. This will certainly get fixed at some point. However, since it does not affect the actual compilation, only the error reporting, it is currently not a high priority.

Although it is possible, it is not recommended to directly output scripts (such as Perl/Python scripts) into the installation destination. It is prudent to always test locally and run the extra install steps when satisfied. The exception is generating web pages. Web pages need to be viewed through a browser anyway, so it is convenient to have output_dir directly point to your web root.

5.3 mydef_make

When projects grow to contain more than one output file, a Makefile is helpful to make the edit-compile-debug cycle easier. We believe in keeping things simple, and believe a simplified, hand-edited Makefile is better than using typical build tools. Build tools generate Makefiles without surfacing the decisions. In the effort to accommodate the most complicated projects, they produce the most complicated solutions even for the simplest projects. That is the opposite of "keeping it simple".

Nevertheless, hand-generating a Makefile can be tedious. mydef_make can be used to generate the initial Makefile by scanning all .def files within the directory as well as all subdirectories. It will generate all the rules from def files to output files using mydef_page commands. For simple projects, the Makefile from mydef_make will be good enough. Both the MyDef project and its output module projects are examples where mydef_make is good enough.

When it is not good enough, you are encouraged to hand-edit your Makefile. If you insist on using build tools, you can always opt to have def source files outside of the build tree and have mydef_page output into the build tree. That way, your build tool can work as if you are directly editing the code rather than generating it from def files. There may even appear to be no difference to your colleagues. One could edit the Makefile to have make automatically invoke the build tool upon updates.

If you run mydef_make the first time (when config file does not exist): 


$ mydef_make
Please enter the path to compile into [out]:

Please enter module type [perl]:

Create output folder out ...

mydef_make prompts you for output_dir and module type. It creates a config file and a Makefile. If the output_dir does not exist, it will create it for you.

If you run it again, it will only update Makefile: 


$ mydef_make

5.4 mydef_run

At the opposite end of building big projects, you may be coding a single program that consists of a single file (not necessarily a single def file). In this case, invoking build tools or even generating a Makefile appears to be overkill. All we would like is a single keypress from source to result.

mydef_run is specifically for this purpose. It can be invoked like this: 


$ mydef_run t.def
PAGE: t
    --> [out/t.pl]
perl out/t.pl
Hello  World!

Basically it compiles from def to output, then based on a set of heuristics about the output file type, runs the appropriate compiler or interpreter to execute the program.

Here is an example with C: 


$ mydef_run t.def
PAGE: t
    --> [out/t.c]
gcc -std=c99 -O2 -oout/t out/t.c  && out/t
Hello World!

Here is an example with Java: 


$ mydef_run t.def
PAGE: t
    --> [out/t.java]
javac out/t.java && cd out && java t
Hello World!

Of course not all types of file have a way to run it: 


$ mydef_run t.def
PAGE: t
    --> [./t.txt]
do not know how to run it

Well, at least it is honest and it compiles for you.

If you configure the command to a hotkey in your editor, then the edit-debug cycle is shortened into a single keypress. If you use vim, put this in .vimrc: 


:nmap <F5> :!mydef_run %<CR>

For details of the heuristics or customization, refer to mydef_run.def in the source repository.

It is possible to directly set command line for mydef_run to run. For example: 


page: t
    run: cat t.txt

    $print Hello World!
        

$ mydef_run t.def
PAGE: t
    --> [./t.txt]
cat t.txt
$print Hello World!

Or you may simply specify an argument: 


page: t
    module: perl
    arg: P1 P2 P3

    $foreach $a in @ARGV
        $print argument $a
        

$ mydef_run t.def
PAGE: t
    --> [./t.pl]
perl ./t.pl P1 P2 P3
arg: P1
arg: P2
arg: P3

As a bonus, do you know that you can directly use mydef_run on .pl, .c, or any source code with a known extension? Try it.

6 output_general

In this chapter, we will explain the internals of MyDef.

output_general is the default output module. It essentially only uses the syntax we have covered so far; nothing more.

However, much of the power of MyDef eventually comes from language- or application-specific output modules. So at some point, you will need to understand some of MyDef's internal workings. The output_general module is the starting point for every output module.

6.1 output_general.def 


include: output.def

page: output_general, output_main
    type: pm
    ext: txt
    package: MyDef::output_general

The actual code is in a subcode output_main defined in output.def.

6.2 output.def

File output.def provides boiler-plate code that most output modules will share: 


subcode: output_main
    $global $debug=0
    $global $out
    $global $mode
    $global $page
    $call @package_globals

    $sub get_interface
        return (\&init_page, \&parsecode, \&set_output, \&modeswitch, \&dumpout);

    $sub init_page($t_page)
        $page=$t_page
        # [... omitted code for per page initialization ...]

    $sub set_output($newout)
        $out = $newout

    $sub modeswitch($mode, $in)
        $call @modeswitch

    # ---- All specialized parsing goes here.
    $sub parsecode($l)
        $if $l=~/^\$warn (.*)/
            $call warn, $1
            return
        $elif $l=~/^\$template\s+(.*)/
            # [... omitted code to read-in template ...]
            return
        $call parsecode_debug
        $call parsecode_eval
        $call parsecode

    # ---- Final output, allows for 2nd pass translation
    $sub dumpout($f, $out)
        my $dump={out=>$out,f=>$f}
        $call @dumpout
        MyDef::dumpout::dumpout($dump);

    $call single_blocks
    $call @support_subs

    1;

subcode: parsecode is where we apply preprocessing logic for each line. output.def provides a default stub which simply pushes the line straight to @$out. It is supposed to be overwritten in the actual output module. For output_general, it is good enough: 


subcode:@ parsecode
    push @$out, $l

7 output_perl

output_perl source is kept within the base MyDef repository because, well, MyDef is coded in perl and would require output_perl to compile.

output_perl is also one of the most mature modules, due to mandatory round-trip testing. In addition, because Perl is a very high-level language and embraces practical expressiveness, output_perl is relatively simple.

Perl is a general purpose programming language, therefore provides the usual variable, functions, scopes, if-else switch, loops, etc. The custom syntax created with output_perl can be a good example for output modules for other languages.

7.1 It is OK to write vanilla Perl 


page: t
    my $a = 0.1;
    my $b = 0.2;

$ mydef_run -mperl t.def

And you can check the output t.pl is (almost) exactly as you wrote:

7.2 $print

print is the most fundamental and useful statement in a language -- not because it is essential in the final program, but because it is essential for providing feedback during code development. Programming is a process.

Perl is one of the most straight forward languages. The "Hello world" program that listed in the first chapter of "Programming Perl" is: 


print "Howdy, world!\n";

To most programmers, this is as basic as it can be. But nevertheless, over years of experience, a few wishes do pop up: Is it necessary to type those quotation marks, and '\n', and the semicolons? The annoyance pops up because we do forget or mistype them from time to time and then have the compiler bug us with errors.

Turns out, in most cases, no, it isn't necessary. So in output_perl, we introduced a hack: 


$print Howdy, world!

In modern versions of Perl, there is a new function say, which essentially is print_ln (print with newline). $print achieves the same without it.

There is more to it. What is the output of this: 


$print Howdy, world!\n

You can quickly check it yourself, but the answer is, no, it won't print two newlines. There is a little intelligence in output_perl that only adds newline when newline is missing. By the way, both of the following works as well: 


$print "Howdy, world!"
$print "Howdy, world!\n"

A little flexibility goes a long way.

Now what if we want to print without newline? 


$print Howdy, -
$print world

'-' in the end signals that we do not want newline. We usually want to print with newline, but occasionally we don't. So the philosophy here is to make the default for common scenarios, and go extra for special cases.

Mixing variables into the string still works. In addition, there is a little hack to make print in color easier: 


my $name = "world";
$print Howdy, $green{$name}!

Supported color names include: red, green, yellow, blue, magenta, cyan. You will have trouble if you have a variable named with one of these color names and want to print it. Hopefully that is rare, but if you do, remember that vanilla Perl's print is still there.

Perl's variable interpolation in strings is great. But sometimes we still want to print with a format. For that, we would need to remember another function: printf. $print supports that as well: 


$print "Pi = %.2f", 3.1415926

It is equivalent to: 


printf "Pi = %.2f\n", 3.1415926;

One more thing: sometimes we want to print to a filehandle, such as STDERR. We can still use $print for that. All we need is to set a special macro: 


$(set:print_to=STDERR)
$print Error: did you just want an error?

That's it for $print! If you want further detail, directly consult the source in output_perl.def and search for subcode: parsecode_print. The implementation for all this flexibility is not complicated, thanks to Perl's built-in convenience.

7.3 Optional semicolons

In the previous section, we saw that print not only lets you omit typing quotation marks and '\n', you also get to omit semicolons. In fact, with output_perl, you can optionally omit semicolons for almost every normal Perl statement. Try this: 


my $name = "Alice"
if ($name eq "Alice"){
    $print Howdy, $name
}
else{
    $print Nice to meet you, $name!
}

Surely, MyDef did not add ';' to every line. It employs some simple heuristics. In fact, you can just check what it does in the source: 


subcode: check_termination
    $if $l=~/^\s*$/
        # NOOP
    $elif $l=~/^\s*(for|while|if|else if)\s*\(.*\)\s*$/
        # NOOP
    $elif $l=~/^\s*}/
        # Check the formal block end
        # Inline blocks will get ; appended.
    $elif $l!~/[,:\(\[\{;]\s*$/
        $l.=";";
    $else
        # NOOP

7.4 $if, $elif, and $else

These are syntactic sugar for if-elsif-else statements. They allow us to write control statements in the style of Python rather than C's curly-brace style. Here is an example: 


for(my $i=1; $i<100; $i++){
    $if $i % 15 == 0
        $print fizbuzz
    $elif $i % 3 == 0
        $print fiz
    $elif $i % 5 == 0
        $print buzz
    $else
        $print $i
}

Obviously there is a similar indentation-based syntax for for-loops, but since that is in the next section, we show the example above to demonstrate that there is nothing wrong with mixing vanilla Perl code with the special syntax introduced by output_perl.

It is common to use if-elif-else as poor man's switch. And for big switch block, it is often desirable to break it apart: 


foreach my $l (@lines){
    $if $l=~/^\s*$/
        # NOOP
    $call @l_is_special
    $else
        $print "nothing special"
}

subcode:: l_is_special
    $elif $l=~/^special: .*/
        $print SPECIAL!

That works. But then there is this nagging thing that you always need differentiate the first case, where you should use $if, and the other cases, where you should use $elif. This makes swapping the orders of cases buggy. For remedy, output_perl has another keyword: $case: 


foreach my $l (@lines){
    $call @check_cases
    $else
        $print "nothing special"
}

subcode:: check_cases
    $case $l=~/^\s*$/
        # NOOP

subcode:: check_cases
    $case $l=~/^special: .*/
        $print SPECIAL!

$case becomes $if if it is the first case, and becomes $elif for subsequent cases. For example, the check_cases subcode above generates: 


if ($l=~/^\s*$/){
}
elsif ($l=~/^special: .*/){
    print "SPECIAL!\n";
}

The first $case emitted if, and the second emitted elsif. This lets you freely reorder or add cases without worrying about which one must be $if. Due to its heuristic nature, $case is a little more fragile than $if and $elif.

One of the top bugs is mistyping == as = in if conditions. So output_perl checks for that when it can and gives you warnings: 


my $i=1
$if $i = 15
    $print fizbuzz
            

$ mydef_run t.def
PAGE: t
[t.def:6] assignment in condition [$i = 15]?
    --> [./t.pl]
perl ./t.pl
fizbuzz

It is only a warning, but if you paid attention, you caught the bug!

7.5 $for

First, let's review the vanilla Perl syntax: 


for(my $i=0; $i<10; $i++){
    $print $i
}

MyDef works purely at the text level; it does not truly understand the language semantics as a compiler does. It only understands the text via heuristics -- which is more similar to how the human mind works. As such, MyDef special syntax does not always work. We start with the vanilla Perl syntax example to emphasize that you can always fall back on the standard syntax if it becomes more trouble than help.

That said, let's see what output_perl offers: 


$for my $i=0; $i<10; $i++
    $print $i

Just like the $if syntax, we now can write it in Python style and save the braces. Further: 


$for my $i=0:10:1
    $print $i

That works. In fact, we can drop the keyword my and the increment by 1 is actually the default: 


$for $i=0:10
    $print $i

In fact, the loop variable $i is also the default, so we can drop that too: 


$for 0:10
    $print $i

Or: 


$for 10
    $print $i

The output is exactly the same for all above examples. We did not change Perl, only the syntax.

Just to make sure, the step part works: 


$for $i=0:10:2
    $print $i

The decreasing for-loop works too, but it is a bit tricky. It is tricky because it appears there is not a established convention. For example, what do we think the following does? 


$for $i=10:0:-1
    $print $i

The current implementation in output_perl prints 10, 9, ..., 0. Yep, it loops 11 times instead of 10. We find it easier to reason by taking the literal meaning of "from 10 down to 0." Many may disagree. As said, tricky. But remember, for clarity you can and maybe should use the more verbose version: 


$for $i=10; $i>0; $i--
    $print $i

7.6 $while

$while exist so we could write while-loop in Python style too. 


$while 1
    $print MyDef FOREVER!
    last # maybe not

7.7 Regex capture with ->

When using $if or $while with a regex match, you can capture match groups directly into variables using the -> syntax: 


$if $line=~/^(\w+):\s*(.*)/ -> $key, $value
    $print key=$key, value=$value

This generates: 


if ($line=~/^(\w+):\s*(.*)/){
    my ($key, $value) = ($1, $2);
    print "key=$key, value=$value\n";
}

Without the -> syntax, you would need to manually assign $1, $2, etc. inside the block. The capture syntax works with $while as well: 


$while $text=~/(\w+)/g -> $word
    $print found: $word

Each capture variable is declared with my, so it is scoped to the block.

7.8 $foreach

foreach reads better with a keyword in: 


$foreach $c in split //, "Hello, world!"
    $print $c

It supplies the my keyword and drops parentheses and braces.

$foreach supports several iteration forms:

Form Example Perl equivalent
basic $foreach $x in @list foreach my $x (@list) {
implicit $foreach @list foreach (@list) {
hash $foreach $k while (my ($k, $v) = each %hash) {
indexed $foreach $_i loop with $_i counter
zip $foreach $_i parallel iteration using index

For the indexed form, the index variable must be one of $_i, $_j, or $_k. The zip form iterates over multiple arrays in parallel using index-based access.

7.9 fncode and function arrangement

Curly braces are also used in defining Perl functions -- sub: 


$sub F($x)
    return $x * $x

$print "3: %d", F(3)

Let's check its Perl equivalent: 


sub F {
    my ($x)=@_;
    return $x * $x;
}
printf "3: %d\n", F(3);

You may recall the criticism that Perl does not have function signatures. As far as syntax goes, this lets us define functions with signatures.

The $sub syntax works, but behaves as a normal statement -- just like if or while. Semantically it is a bit unsatisfactory, as $sub merely defines the function rather than having runtime action as other control statements do. Ideally, we would like to have a declarative syntax for functions and move them outside of normal code blocks. In MyDef, we can use fncode: 


page: t
    $print "3: %d", F(3)

fncode: F($x)
    return $x * $x

If you are writing a .pm module, all fncode: definitions are included in the output. However, if you are writing a .pl script, which is the default, only those functions that are used will be included. output_perl detects which functions are being used with very simple heuristics: 


fncode: check_fcall($l)
    $while $l=~/\b(\w+)\(/g
        $call add_function, $1

In case the heuristics do not work well and miss a function that you do use, you can always add the function explicitly with $list: 


page: t
    $list F
    $print "3: %d", F(3)

fncode: F($x)
    return $x * $x

7.10 $global and $use

There is this religion that we should avoid global variables. The practitioners of MyDef do not believe in extreme stances. Globals are certainly convenient. If we do use globals, we definitely would like to define them close to where they are relevant rather than pile all of them at the top. Language semantics, on the other hand, do make sense to have all globals piled at the top. To help, output_perl provides $global to make declaration (and initialization) of global variables declarative. 


page: t
    $print "3: %d", F(3)

fncode: F($x)
    $global $Offset = 10
    return $x * $x + $Offset

We certainly do not want re-declare and reset $Offset every time the function is called. The Perl output equivalent is: 


use strict;
our $Offset = 10;

sub F {
    my ($x)=@_;
    return $x * $x + $Offset
}

printf "3: %d\n", F(3);

Similarly, $use made importing packages declarative so you could embed certain package dependence into relevant code and be confident that they all will be gathered to their rightful place.

7.11 std_perl.def

Finally, not all customization need to happen at the internal level. We can have customization coded in MyDef macro syntax and have them included in the def file. For each output module, there is one standard library that is always included automatically. For perl, that is std_perl.def. It is located at deflib/ in the repository and at $MYDEFLIB in your installed destination.

It is easy enough for you to open that file and see for yourself what is in it. It is a collection of convenience macros; some are frequently used while others are rarely used. Those rarely used will probably get pruned away at some point.

The most used two subcodes are subcode: open_r and subcode: open_w. subcode: open_r allows short code for opening file and read it line by line: 


&call open_r, t.txt
    $if /(\w+), (\w+)/
        $print Hello $2 $1!

subcode: open_w is similar but obviously it can't write line by line for you: 


&call open_w, t.txt
    $(set:print_to=Out)
    $print Hello, world!
    $print Hello, world, again.

In is the default input file handle, and Out is the default output file handle.

If you just want to read in the whole file in a scalar, you can use subcode: get_file_in_t: 


$call get_file_in_t, t.txt
$print [$t]

There is also get_file_lines that slurps entire text file into @lines array. 


$call get_file_lines, t.txt
$print "Got %d lines", $#lines+1

8 output_c

output_c lives in its own repository, github.com/hzhou/output_c. Install it the same way as MyDef itself -- clone it, then run mydef_make, make, and make install inside it. It provides module: c (and module: cpp for C++).

C is a lower-level language than Perl. It has more syntax to type -- semicolons, braces, parentheses, format strings, and, above all, type declarations. Much of what output_c adds is aimed at that noise, so the code that remains says what the program does.

8.1 It is OK to write vanilla C

A page with module: c compiles to a .c file. basic_frame, defined in std_c.def, supplies the main function and puts the page code inside it. (It is the default frame, so naming it is optional -- see the next section.) 


page: t, basic_frame
    module: c

    int a = 3;
    if (a > 2) {
        printf("a is big\n");
    }
        

$ mydef_run t.def
PAGE: t
    --> [./t.c]
gcc -std=c99 -g -O2 -o ./t ./t.c  && ./t
a is big

and t.c is what you would expect: 


#include <stdio.h>
#include <stdlib.h>

int main(int argc, char** argv)
{
    int a = 3;
    if (a > 2) {
        printf("a is big\n");
    }
    return 0;
}

As with output_perl, semicolons are optional, and $if, $elif, $else, and $while let you drop the parentheses and braces: 


page: t, basic_frame
    module: c

    $local int a = 3
    $if a > 2
        printf("a is big\n")
    $elif a > 1
        printf("a is medium\n")
    $else
        printf("a is small\n")
    $while a > 0
        a--

output_c also warns about the classic = vs == mistake: $if a = 0 produces the warning Assignment in [a = 0], possible bug?. For a do ... while loop there is $dowhile cond.

8.2 Scripts, programs, and libraries

When a page does not name a frame, MyDef uses basic_frame if one is defined -- and std_c.def defines one. So every C page gets a main function by default, and page: t means the same as page: t, basic_frame. The default serves the most common use: quick programs run with mydef_run.

For a one-off script, even the page: line is optional. A .def file without any page: becomes a page named after the file, and its top-level code becomes the body of main: 


module: c

$print Hello from a script
$local int n = 6
$print n*7 = ${n*7}
        

$ mydef_run script.def
PAGE: script
    --> [./script.c]
gcc -std=c99 -g -O2 -o ./script ./script.c  && ./script
Hello from a script
n*7 = 42

That makes C about as quick to try out as a scripting language.

To write C code without main -- a library, or a file to be linked into another program -- give the page the frame -, which means "no frame". Since nothing calls the functions, tell output_c which ones to include, either one by one with $list or all at once with autolist: global: 


page: mylib, -
    module: c
    autolist: global

fncode: add(a, b: int): int
    return a + b

fncode: mean(a, b: double): double
    return (a+b)/2
        

int add(int a, int b);
double mean(double a, double b);

int add(int a, int b)
{
    return a + b;
}

double mean(double a, double b)
{
    return (a + b) / 2;
}

autolist: page is similar but includes only the fncode: blocks defined inside the page, which is useful when one .def file holds several pages. Any page code outside functions goes to the top level of the file.

8.3 $print

$print is meant for debug printing -- the quick "what is in this variable now" line that we add and remove many times while developing. For that it offers two conveniences: variables are interpolated directly into the text, and the newline is added automatically. 


$local int n = 3
$local double x = 1.5
$local char *s_name = "Bob"
$print n = $n, x = $x, name = $s_name

The format for each variable is picked from its type: 


printf("n = %d, x = %g, name = %s\n", n, x, s_name);

A few more forms: 


$print "x = %.2f", x        # printf format, newline still added
$print Loading -            # trailing "-": no newline
$print arr[2] = ${arr[2]}   # ${...} for an expression
$dump n, x                  # prints "    :n=3, x=1.5"

The two styles can be mixed. In the quoted form, % formats take their arguments from the list after the string, and $var is filled in where it appears -- handy when one value needs a specific format and the rest do not: 


$print "x = %.2f, n = $n, name = $s_name", x
$print "[%5d] [$n] [%-6s]", n, s_name
        

printf("x = %.2f, n = %d, name = %s\n", x, n, s_name);
printf("[%5d] [%d] [%-6s]\n", n, n, s_name);

Mixing requires the quotes. Without them, $print does not see where the text ends and the arguments begin: $print x = %.2f, n = $n, x produces broken C and a Missing 1 fmt arguments warning.

To print to another stream, set the print_to macro, e.g. $(set:print_to=stderr).

$print relies on knowing the type of what it prints. When it cannot tell -- an expression such as ${2*n}, a function call, or a variable whose declaration MyDef did not see -- it warns and falls back to %d: 


[t.def:14] get_var_fmt: unhandled 2*n - , default to %d

At that point $print is going out of its way. Don't fight it -- write a regular printf (or the printf form of $print) with an explicit format: 


printf("twice = %d\n", 2*n)
$print "sqrt = %f", sqrt(r)

8.4 $for and $foreach

$for takes a range start:end:step. The end is exclusive, and the loop variable is declared in the loop: 


$for 10             # i = 0 ... 9
$for i=0:10         # i = 0 ... 9
$for j=0:10:3       # j = 0, 3, 6, 9
$for k=9:0:-1       # k = 9 ... 0

which become, for example, for (int j = 0; j < 10; j += 3). As in output_perl, a decreasing range includes both ends: 9:0:-1 counts from 9 down to 0. The convention is not obvious, so when in doubt write the full C form -- it works too: 


$for i=9; i>=0; i--
    $print $i

$foreach iterates over an array whose size MyDef knows, e.g. one created with $allocate (see below).

8.5 Variables and type inference

C wants every variable declared with a type, at the top of its scope. In real code, many of those declaration lines carry no information that the name does not already convey: i is an int loop counter, s_name is a string, f_scale is a float. output_c lets the names carry the types and writes the declarations for you, so the code stays short and readable.

$local declares variables at the top of the current function; $global declares them at the top of the file; $my declares them in the current block. A variable that is assigned without being declared is declared automatically. 


page: t, basic_frame
    module: c

    $local i, n_count, f_scale, s_name, b_done
    $global g_total = 0
    k = 10
    ratio = 0.5

generates: 


...
int g_total = 0;

int main(int argc, char** argv)
{
    int i;
    int n_count;
    float f_scale;
    char *s_name;
    bool b_done;
    int k;
    float ratio;

    k = 10;
    ratio = 0.5;
    return 0;
}

The type comes from the name first and, failing that, from the assigned value (0.5 is a float, "text" a char *). The built-in naming rules include:

Name Type
i j k m n int
f d float / double
c and c_... unsigned char
s and s_... char *
b_... is_... has_... bool
n_... i_... int
f_... d_... float / double
n4_... u8_... i64_... int32_t / uint64_t / int64_t
size_... time_... file_... size_t / time_t / FILE *
p_... + a prefix pointer to that type: pn_list is int *

The full rules are in types.def in the MyDef and output_c sources.

Project naming conventions

The built-in rules are a starting point. The real value comes when a project settles on its own naming convention and registers it. $register_name gives the type of an exact name; $register_prefix gives the type of every name that starts with a prefix and an underscore: 


subcode: _autoload
    $register_name(node) struct Node
    $register_prefix(pt) struct Point
    $register_prefix(len) size_t

page: t, basic_frame
    module: c
    $struct(Point) f_x, f_y
    $struct(Node) n_value, p_next

    $local node, p_node, pt_start, pt_end, len_name
        

struct Node node;
struct Node *p_node;
struct Point pt_start;
struct Point pt_end;
size_t len_name;

p_node became a pointer to node's type, following the p_ rule. Once the convention is registered, code throughout the project stays free of declarations -- and the convention itself is enforced, because a name that breaks it gets the wrong type and the compiler complains.

Explicit types

Inference is heuristic. A name that matches no rule, and has no value to infer from, gets no type at all (the declaration comes out as just foo;). A variable assigned from a function call may also miss, since the function's return type may not be known yet. Whenever that happens, or whenever you prefer, declare the type explicitly -- any of these forms work: 


$local int count, char grade, double ratio = 0.5
$local foo: long
$my a: char[10]
        

int count;
char grade;
double ratio = 0.5;
long foo;
char a[10];

Note that a declaration written as plain C with a semicolon, such as int a = 3;, is passed through untouched, and MyDef does not record its type. Without the semicolon, double x = 0.5 is recognized, and the declaration is moved to the top of the function.

8.6 fncode and prototypes

fncode: defines a C function. Parameter types follow the same naming rules, or can be given explicitly; the return type is inferred from the return statement or given after a colon. Prototypes are generated at the top of the file, so functions can be defined in any order: 


page: t, basic_frame
    module: c
    n_area = rect_area(3, 4)
    $print area = $n_area
    greet("World")

fncode: rect_area(n_w, n_h)
    return n_w * n_h

fncode: mean(a, b: double): double
    return (a+b)/2

fncode: greet(s_name)
    $print Hello $s_name!
        

int rect_area(int n_w, int n_h);
void greet(char *s_name);
...
int rect_area(int n_w, int n_h)
{
    return n_w * n_h;
}

Parameters can be grouped with semicolons: 


fncode: A(c, f; int a1, a2; b1, b2: float)
        

void A(unsigned char c, float f, int a1, int a2, float b1, float b2)

c and f get their inferred types, a leading type (int a1) or a trailing one (b2: float) applies to the whole group.

As in output_perl, only functions that are actually called are included -- mean above is left out. The detection is a simple scan of the code lines for name(. It misses a function that is used without a direct call -- one passed as a callback or stored in a function pointer, for example. Add such functions explicitly with $list: 


$list rect_area, mean

8.7 Headers, macros, and structures

$include adds a header at the top of the file, with or without the .h: $include math becomes #include <math.h>. What inferred types need is added automatically -- stdint.h for int32_t and friends, and a bool typedef when a bool variable is used. Plain C preprocessor lines -- #include, #define, #ifdef, and the rest -- are recognized and passed through, even though # otherwise starts a MyDef comment.

$struct(Name) fields declares a structure, with field types following the naming rules: 


$struct(point) f_x, f_y, s_label
$local struct point pt
        

struct point {
    float f_x;
    float f_y;
    char* s_label;
};

To link libraries, set lib_list on the page. It is passed to the compiler as is: 


page: t, basic_frame
    module: c
    lib_list: -lm
    $include math
    $local double r = 2.0
    $print "sqrt = %f", sqrt(r)

8.8 std_c.def and the C library

std_c.def is loaded automatically for module: c. Besides basic_frame, it has small helpers such as $call assert, cond, $call die, msg, and $call warn, msg. $allocate(n) pn_array allocates an array with calloc (with an optional initial value, $allocate(n, 0) pn_array), and records its size so $foreach pn_array can loop over it.

Larger pieces live in optional libraries under c/, pulled in with include: -- for example include: c/string.def, c/hash.def, c/darray.def, c/regex.def, c/getopt.def, and c/thread.def. The tests/ folder of the output_c repository has working examples of most features.

9 output_www

output_www lives in its own repository, github.com/hzhou/output_www, and is installed the same way as output_c (mydef_make, make, make install). It provides three modules: module: www for HTML pages, module: js for JavaScript, and module: php for PHP. This manual itself is written with output_www -- see manual/mydef.def in the MyDef repository.

HTML is a markup language. Most of its noise is closing tags, and indentation already shows the nesting, so the main thing output_www adds is tags written as indented blocks.

9.1 A first page 


page: hello
    module: www
    title: Hello

    $h1
        Hello, World!
    $p
        My first MyDef page.

mydef_page hello.def writes hello.html: 


<!doctype html>
<html>
    <head>
        <meta charset="utf-8">
        <title>Hello</title>
    </head>
    <body>
        <h1>
            Hello, World!
        </h1>
        <p>
            My first MyDef page.
        </p>
    </body>
</html>

As with output_c, the page gets a default frame: basic_frame from std_www.def writes the <html>, <head>, and <body> skeleton and puts the page code in the body. title: sets the page title; without it, the title is the page name. Plain text and raw HTML lines are passed through as they are.

9.2 Tags

A tag is written as $tagname followed by a comma-separated list of attributes, with the content indented below it: 


$p hint, #intro
    A paragraph with class and id.
$a href:https://example.com, target:_blank
    a link
        

<p class="hint" id="intro">
    A paragraph with class and id.
</p>
<a href="https://example.com" target="_blank">
    a link
</a>

Each item in the attribute list is read by its form:

Form Meaning Example
bare word CSS class $div note → class="note"
#name id $div #box → id="box"
key:value attribute $img src:logo.png
"text" short content on the same line $li "one" → <li>one</li>
/ empty element $div #box, / → <div id="box"></div>

$img and $input are written as self-closing tags. $input gets type="text" unless a type is given, and its quoted text becomes the placeholder.

Tags known by name are the common ones: html head body h1-h5 p pre div span form label fieldset button input textarea select option table tr td th ol ul li img a center b style. Any other tag is written with $tag: $tag nav, main-nav gives <nav class="main-nav">.

The attribute list is split at commas, and text in quotes is read as a key:value attribute if it contains a colon. When content has commas or colons -- including content produced by a macro -- put it in the indented block instead of quotes: 


$td "Note: see below"       # wrong: read as an attribute "Note"
$td
    Note: see below         # right

9.3 CSS

CSS: lines add style rules. They can appear anywhere in the page, typically next to the elements they style, and are all gathered into one <style> block in the head. Rules for the same selector are merged, and a .css file name becomes a stylesheet link: 


$p hint
    CSS: .hint {color: #888}
    CSS: .hint {font-size: small}
    styled text
CSS: theme.css
        

<link rel="stylesheet" type="text/css" href="theme.css" />
<style>
    .hint {color: #888; font-size: small}
</style>

One catch: CSS: ... has the form of a page attribute, so CSS: lines placed right below the page: line, before any other code, are taken as page attributes and silently lost (see Collisions with target-language syntax in the Syntax chapter). Put them after the first line of content, or collect them in a subcode and $call it, as this manual does.

9.4 JavaScript

A $script block switches to JavaScript. Inside it, the code is handled by output_js, which gives JavaScript the same conveniences as the other modules -- optional semicolons, and $if, $for, $while, and $function without parentheses and braces: 


$script
    var n = 3
    $if n > 2
        console.log("big")
        

<script type="text/javascript">
    var n = 3;
    if(n > 2){
        console.log("big");
    }
</script>

For pages with real scripting, use js_frame. It adds a <script> block to the head and runs the js_onload subcode when the page loads. Code in jscode: subcodes is JavaScript, and $global declares a global variable at the top of the script: 


page: counter, js_frame
    module: www
    title: Counter
    $button #btn, "Click me"
    $span #count, "0"

jscode:: js_onload
    $global clicks = 0
    &call on_click, btn
        clicks++
        $(id:count).innerHTML = clicks
        

<script type="text/javascript">
    var clicks = 0;
    window.onload = function(){
        document.getElementById("btn").addEventListener("click", function(event){
            clicks++;
            document.getElementById('count').innerHTML = clicks;
        }, false);
    };
</script>

std_js.def provides these helpers. The macros $(id:x), $(value:x), $(style:x), $(show:x), and $(hide:x) are short for document.getElementById expressions. The block subcodes on_click, on_change, setf, ajax_get, and ajax_post wrap the usual event and request patterns. js_frame also calls the optional subcodes js_global and css_global.

A page with module: js produces a standalone .js file. $global works there too: the var declarations go at the top of the file.

9.5 PHP

PHP support is simpler and less developed. A page with type: php is written as a .php file, and in its HTML text, a $var becomes <?php echo $var ?>: 


page: greet
    module: www
    type: php
    $h1
        Hello, $name!
        

<h1>
    Hello, <?php echo $name ?>!
</h1>

For a page that is all PHP, use php_frame, which compiles the page code as PHP; tags in PHP code are written out with echo. phpcode: subcodes are also PHP, and can be called from an HTML page: the output switches into <?php ... ?> for the call and back to HTML after it. $form adds method="POST" when no method is given; without an action, the form submits to the current URL.

9.6 std_html.def and other libraries

std_www.def is loaded automatically and brings in std_html.def, std_js.def, and std_php.def. std_html.def has inline macros for the most common markup:

Macro Output
$(a:text,url) <a href="url">text</a>
$(url:u) <a href="u">u</a>
$(anchor:name) <a name="name"></a>
$(code:text) <code>text</code>
$(b:text) / $(em:text) <strong> / <em>
$(img:src) <img src="src" />

It also has form helpers (input_text, input_pass, input_checkbox, input_radio, input_hidden, input_submit, input_option) and js_src for loading a script file: 


$call js_src, app.js
$form action:save.php
    $call input_text, username
    $call input_checkbox, remember, Remember me
    $call input_submit, Save

Two optional libraries are included with include:. html/code.def provides codeprint, which formats code listings (with highlighting for mydef code) -- every code example in this manual goes through it: 


include: html/code.def

html/markdown.def converts a block of Markdown to HTML, using an external markdown_translate.pl script.

10 output_python

output_python lives in its own repository, github.com/hzhou/output_python, and is installed the same way as output_c (mydef_make, make, make install). It provides module: python, which writes Python 3.

Python already has little syntax noise, so output_python adds less than the other modules. What it does add is the shared MyDef toolkit -- $print, $for, regex capture, and the file and import bookkeeping -- in the same form as in output_perl and output_c, so a program can move between them with few changes. Its companion script perl_to_python converts a module: perl page into a module: python one.

10.1 It is OK to write vanilla Python

A page with module: python compiles to a .py file. As with output_c, the page code goes into a main function, from the default basic_frame in std_python.def. A .def file without a page: line works too, as a page named after the file. 


page: t
    module: python

    n = 3
    if n > 2
        print("n is big")
    $if n > 5
        print "huge"
    $elif !n
        print "zero"
    $else
        n++
        $print n=$n, n*7=${n*7}
        

$ mydef_run t.def
PAGE: t
    --> [./t.py]
python ./t.py
n is big
n=4, n*7=28

and t.py is: 


def main():
    n = 3
    if n > 2:
        print("n is big")
    if n > 5:
        print("huge")
    elif not n:
        print("zero")
    else:
        n+=1
        print("n=%s, n*7=%s" % (n, n*7))

# ---------------------------------------------------------
if __name__ == "__main__":
    main()

Plain Python passes through, as long as it is indented properly. On top of it:

  • The trailing colon after if, elif, else, while, for, and def is optional.
  • print x becomes print(x).
  • n++ and n-- become n+=1 and n-=1.
  • $if, $elif, $else, and $while work as in the other modules, and ! in their condition becomes not.
  • $while cond; step puts step at the end of the loop body.

The comment rules of the Syntax chapter apply: a # with spaces on both sides starts a MyDef comment, even inside a string. Write "a \x23 b" for such a string.

10.2 $print

$print is for debug printing. It fills in $var and ${expr} and adds a newline, as in the other modules. A trailing - leaves the newline out. $print writes a % format; since Python formats any value with %s, there is no type to infer. Related directives: 


$print n=$n, root=${sqrt(n)}
$print no newline-
$dump n, L
$warn cannot open $fname
$die bad input: $s
        

print("n=%s, root=%s" % (n, sqrt(n)))
print("no newline", end='')
print("n = %s, L = %s" % (n, L))
print("cannot open %s" % fname, file=sys.stderr)
raise Exception("bad input: %s" % s)

import sys is added for $warn. When one value needs a specific format, quote the text and give the format arguments after it, as in output_c: 


$print "x = %.2f, n = $n", x
        

print("x = %.2f, n = %s" % (x, n))

Since a % can start a format, write %% for a literal percent sign: $print done: 100%%. (A lone % followed by a space and a letter, as in 50% done, is read as the printf format % d and triggers a Missing 1 fmt arguments warning.) When $print gets in the way, write a plain print() or an f-string.

10.3 $for and $do

$for turns the usual loop forms into range, enumerate, and zip. $foreach is the same as $for.

MyDef Python
$for i=0:10 for i in range(10):
$for i=2:10 for i in range(2,10):
$for i=0:10:2 for i in range(0,10,2):
$for N for _i in range(N):
$for x in L for x in L:
$for i, x in L for i, x in enumerate(L):
$for x, y in A, B for x, y in zip(A, B):
$for i, a, b in A, B for i, a, b in zip(range(len(A)), A, B):

With two variables and one list, $for uses enumerate when the first variable is named i through n; with as many lists as variables, it uses zip.

$do makes a block that runs once, which you can leave early with break: 


$do
    $if not ready
        break
    process()
        

while 1: # $do:
    if not ready:
        break
    process()
    break

10.4 Functions, $global, and $import

fncode: defines a module-level function, written after main in the order they are first called. As with output_c, a function is included only when the code calls it; unused ones are left out. A def inside the page code is an ordinary nested function. 


page: t
    module: python

    $import sqrt from math
    $global count = 0
    bump()
    bump()
    $print count = $count, root = ${sqrt(add(7, 9))}

fncode: add(a, b)
    return a + b

fncode: bump
    $global count
    count += 1

fncode: unused
    pass
        

from math import sqrt

count = 0

def main():
    global count
    bump()
    bump()
    print("count = %s, root = %s" % (count, sqrt(add(7, 9))))

# ---- subroutines --------------------------------------------
def bump():
    global count
    count += 1

def add(a, b):
    return a + b

$global count = 0 puts the assignment at module level and global count in the current function. Other functions that assign to it need their own $global count.

$import lines can appear anywhere; they are collected at the top of the file, with duplicates removed. $import numpy as np and $import sqrt from math (for from math import sqrt) are both accepted. $try_import yaml wraps the import in try and sets has_yaml to True or False. Modules used as re., os., sys., copy., or glob. are imported automatically.

10.5 Regex capture with ->

The Perl-style match and capture from output_perl (see its section on regex capture) works in $if and $elif, and becomes re.search: 


$if s=~/Hello\s+(\w+)/ -> who
    $print Match: $who
        

if re.search(r'Hello\s+(\w+)', s):
    m = re.search(r'Hello\s+(\w+)', s)
    who = m.group(1)
    print("Match: %s" % who)

A pattern anchored with ^ becomes re.match. For a lexer, $if_match pattern matches at position src_pos in src, precompiles the pattern, and on success advances src_pos and leaves the match in m.

std_python.def is loaded automatically. Its file subcodes take the file name as a Python expression, so a literal name needs quotes: 


&call open_W, "words.txt"
    $print apple pie
    $print banana split
    $print apple tart
counts = {}
&call open_r, "words.txt"

$ mydef_run t.def
...
    --> [words.txt]
